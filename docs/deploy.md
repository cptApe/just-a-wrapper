# Deploy to Vercel

1. Import your fork into Vercel as a Next.js project. Select your release branch and use `pnpm build`. Configure the required keys from `.env.example`, your HTTPS `NEXT_PUBLIC_APP_URL`, your product name in `NEXT_PUBLIC_BRAND_NAME`, your support address in `SUPPORT_EMAIL`, and keys for enabled providers. The repository ships placeholders for the name and support address, and a production build refuses them. Keep preview and production resources separate. Leave development, admin and E2E flags disabled.
2. Apply migrations before deploying code that requires them. In a trusted shell configured for the target database, run `pnpm db:migrate`. Use a nonempty `DATABASE_URL_UNPOOLED` for the direct Neon URL, or omit it to use `DATABASE_URL`. This records and applies pending migrations; the Vercel build does not migrate for you. Review migration SQL and backup requirements before applying changes to user data.
3. Configure Anthropic and run `pnpm seed:agents` against the intended account. Store the printed tier Agent IDs and Environment ID in Vercel. Seeding updates Agents by name; updating an existing Environment requires `--update-environment`. Set `MCP_PROXY_URL` to your deployment's `/api/mcp/composio` before seeding if connected apps are enabled. Its exact address must match the app and vault credentials.
4. Configure enabled provider callbacks: Google `/api/auth/callback/google`, Anthropic `/api/webhooks/anthropic`, Composio `/api/webhooks/composio`, Stripe `/api/webhooks/stripe`. Set the corresponding webhook secrets. Verify a Resend sender for email delivery. Stripe catalog creation uses `pnpm seed:stripe` for test mode or explicit `pnpm seed:stripe --live` for live billing. Configure `CRON_SECRET` for the schedules declared in `vercel.json`.
5. Run `pnpm verify`, deploy and test `/login`, a fresh workspace, a chat reply and a file upload. Test each enabled provider and inspect webhook delivery failures. Environment changes require redeployment; public settings are embedded at build time.

Keep credentials in the host's environment settings, never in deployment notes or Git.

Your brand is configuration, not code. `NEXT_PUBLIC_BRAND_NAME` and `NEXT_PUBLIC_APP_URL` are fixed at build time, so changing them takes a redeploy. Emails come from `EMAIL_FROM`, or `<name> <hello@<domain of NEXT_PUBLIC_APP_URL>>` when it is unset. `SUPPORT_EMAIL` is the Get help link, every email footer and the contact line of the legal pages; a deployment with the admin console can change it on the Brand page without a redeploy, and production sets the env var. Run `pnpm validate:config` to list any value still on its placeholder. Set `NEXT_PUBLIC_BRAND_NAME` before `pnpm seed:stripe --live`, because Stripe product names follow it.

Choose how the deployment sells with `BILLING_MODE`: `subscriptions` (monthly plans, the default) or `credits_only` (one-time credits, no plans). A deployment with the admin console can switch it on the Pricing page, and a stored choice wins over the env var. Production has no admin console, so it sets the env var. In subscription mode, run `pnpm seed:stripe` (and `--live` for production) after setting the mode and after any change to `PLANS`, `CREDIT_PACKAGES` or `MARGIN_PERCENT`; the admin overview says when Stripe's plan prices differ. Credits-only mode needs only the top-up product the same command creates, and never archives plan prices that existing subscribers pay on.

Keep Stripe Customer Portal **Switch plan** and **Update quantities** off in both modes. Plans change in the app, where the confirmed charge and the credit grants apply; credits-only mode offers no plan changes, so an existing subscription stays on the package it already has. The repository opens the default Portal configuration and cannot enforce the account's Dashboard settings. Stripe documents these controls in [Configure the customer portal](https://docs.stripe.com/customer-management/configure-portal).

Google sign-in is optional. Omit both `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` to disable its provider; the button stays and says which keys turn it on. Set both to enable it; an incomplete pair fails configuration validation. A local install needs no email service: run `pnpm dev`, enter your email at `/login`, and paste the code printed in the server log. Hosted email-only sign-in requires `RESEND_API_KEY` and a verified `EMAIL_FROM`; console codes are never enabled in production. With neither Resend nor Google, a deployment starts but cannot sign users in.

## Scheduled jobs

`vercel.json` runs `/api/cron/billing` at `0 3 * * *`, and `/api/cron/purge` and `/api/cron/recovery` at `0 4 * * *`. Every route requires `Authorization: Bearer $CRON_SECRET` and answers 401 when the secret is unset, so set `CRON_SECRET` on every deployment. The daily schedule fits Vercel Hobby. Paid plans or an external scheduler can run recovery at `*/5 * * * *`. Other hosts need an equivalent authenticated scheduler.

The billing job recovers pending settlements, top-ups, budget syncs and stale tool deliveries before replaying sessions until its time budget expires. Tool calls waiting for confirmation are excluded. An interrupted executor is reported as an unknown outcome and never re-executed automatically. Scheduled tasks run without `ANTHROPIC_WEBHOOK_SECRET`; set it so run results arrive immediately instead of at the next recovery sweep.

## Stripe webhook events

`pnpm validate:config` checks that an enabled Stripe endpoint matches this deployment's `/api/webhooks/stripe` URL and subscribes to every event in `src/features/billing/lib/stripe-webhook-events.ts`: `customer.deleted`, `invoice.paid`, `invoice.payment_failed`, `checkout.session.completed`, `payment_intent.succeeded`, `payment_intent.payment_failed`, `customer.subscription.deleted`, `customer.subscription.updated`, `charge.refunded`, `refund.updated`, `refund.failed`, and all five `charge.dispute.*` events (created, updated, closed, funds_withdrawn, funds_reinstated). The environment admin page checks the same contract. Stripe CLI forwarding is useful locally but does not replace the deployed endpoint check.

## Hosted settings

`NEXT_PUBLIC_ENABLE_ADMIN_ROUTES=true` is refused on Vercel production and self-hosted production with a non-loopback app URL. Local `next build` / `next start` with `NEXT_PUBLIC_APP_URL` on localhost, 127.0.0.1 or [::1] may enable it, as may explicit Vercel previews. On a Vercel preview, or any host that is not loopback, the admin console requires a signed-in user. `NEXT_PUBLIC_ENABLE_DEV_ROUTES=true` follows the same production rule, and the dev routes also answer only local requests. `DATABASE_WS_PROXY` follows it too: it sends database traffic through a local proxy without TLS, so leave it unset on every deployment.

The page image CSP is set by `src/proxy.ts` at runtime. Self-hosted images may be built without `BLOB_READ_WRITE_TOKEN`; supply the token when starting the server so the policy permits that private store.
